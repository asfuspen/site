The device code flow exists to solve a legitimate problem: signing in on equipment that has no keyboard or browser. The [Microsoft identity platform documentation](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-device-code) mentions smart TVs, IoT devices and printers. The device shows a code, the person opens a sign-in page on another device, types the code and authenticates there. Meanwhile, the device polls the token endpoint until it receives access.

The problem is that nothing in this flow guarantees that whoever generated the code is the one who will use it. If the attacker generates the code and convinces the victim to type it, the victim completes a full sign-in, MFA included, on the real Microsoft page, and the tokens go to the attacker. MITRE ATT&CK covers this variant under [Spearphishing Link (T1566.002)](https://attack.mitre.org/techniques/T1566/002/), naming it "device code phishing".

## The Storm-2372 case

In February 2025, Microsoft Threat Intelligence [published an analysis of a campaign](https://www.microsoft.com/en-us/security/blog/2025/02/13/storm-2372-conducts-device-code-phishing-campaign/) attributed to Storm-2372, active since August 2024. A July 2026 update to the same post now assesses the group as an initial access sub-cluster of Midnight Blizzard. According to the report:

1. The attacker built rapport with the victim by posing as someone relevant to them, on messaging apps such as WhatsApp, Signal and Microsoft Teams.
2. Next, they sent a fake invitation to an online meeting or event. The "meeting code" was actually a device code generated by the attacker.
3. When the victim typed the code on the legitimate page, the attacker received the access and refresh tokens and could read email and cloud storage without the password.
4. With the account taken over, the group sent new internal phishing messages and used Microsoft Graph to search for messages containing terms such as "password", "admin", "credentials" and "secret", exfiltrating what it found.

The report also explains that the group switched to the Microsoft Authentication Broker client ID, which allowed it to register an attacker-controlled device in Entra ID and obtain a Primary Refresh Token. Targets included government, NGOs, technology, defense, telecommunications, health, higher education and energy.

The code is short-lived: the flow documentation states that the user has 15 minutes to sign in from the moment the request is sent. That is why the attacker needs a real-time conversation or an invitation with a set time.

## First step: measure legitimate usage

Before blocking, find out who uses the flow today. The page on [authentication flows in Conditional Access](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-authentication-flows) suggests creating the policy in report-only mode or filtering the sign-in logs by authentication protocol. In Sentinel, the `AuthenticationProtocol` column exists in both the [SigninLogs](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/signinlogs) and [AADNonInteractiveUserSignInLogs](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/aadnoninteractiveusersigninlogs) tables, and `deviceCode` is one of the documented values.

```kql
SigninLogs
| where TimeGenerated > ago(30d)
| where AuthenticationProtocol == "deviceCode"
| summarize SignIns = count(), Successes = countif(ResultType == "0"),
    Users = dcount(UserPrincipalName), FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated)
    by AppDisplayName
| order by SignIns desc
```

The result shows which applications depend on the flow and how many people use them. The 30-day window is my starting point, not an official value; adjust it to your workspace retention.

## Blocking with Conditional Access

Microsoft's recommendation is straightforward: allow device code flow only where necessary and block it wherever possible. The [Block authentication flows](https://learn.microsoft.com/en-us/entra/identity/conditional-access/policy-block-authentication-flows) guide describes the policy:

1. Sign in to the Microsoft Entra admin center as at least a Conditional Access Administrator.
2. Go to **Entra ID > Conditional Access > Policies** and select **New policy**.
3. Under **Users or workload identities**, include all users and exclude the emergency access (break-glass) accounts and other necessary accounts. The guide asks you to audit this exclusion list regularly.
4. Under **Target resources**, include **All resources**.
5. Under **Conditions > Authentication Flows**, set **Configure = Yes** and select **Device code flow**.
6. Under **Grant**, select **Block access**.
7. Create the policy in **Report-only**, check the impact, then switch it to **On**.

When there is a legitimate use that cannot be replaced, the concept page gives an example exception: if Android-based meeting room devices depend on the flow, block it everywhere except for Android devices in a specific network location.

Two points from the documentation prevent surprises after enabling the policy:

- **Protocol tracking.** A session started with a device code is tagged, and the tag persists through token refreshes. A later request that does not use the flow can still be blocked by the policy. In that case the user gets the `AADSTS530036` error, and the documentation says the block is expected. In the log, the "original transfer method" property shows "Device code flow"; in the Sentinel tables, the matching column is `OriginalTransferMethod`.
- **Device registration.** Since September 2024, authentication flow policies that target all resources also apply to the Device Registration Service. If your organization registers devices using device code, exclude that resource from the policy.

## Detection: first use per user

While the policy is in report-only mode, or for the accounts left out of it, it is worth alerting when a user completes a device code sign-in for the first time in 30 days:

```kql
let Lookback = 30d;
let KnownUsers = SigninLogs
    | where TimeGenerated between (ago(Lookback) .. ago(1d))
    | where AuthenticationProtocol == "deviceCode"
    | where ResultType == "0"
    | distinct UserPrincipalName;
SigninLogs
| where TimeGenerated > ago(1d)
| where AuthenticationProtocol == "deviceCode"
| where ResultType == "0"
| where UserPrincipalName !in (KnownUsers)
| project TimeGenerated, UserPrincipalName, AppDisplayName, IPAddress,
    RiskLevelDuringSignIn, ConditionalAccessStatus
| order by TimeGenerated desc
```

During triage, compare the IP and application with what the user normally uses, and ask them whether they recently typed a code. The Storm-2372 post also includes Defender XDR hunting queries that correlate clicks on device login URLs with risky sign-ins and look for devices registered through the Device Registration Service.

## If an account was compromised

Changing the password is not enough, because the attacker holds tokens. The mitigations in Microsoft's report include revoking the user's refresh tokens with `revokeSignInSessions`, requiring MFA with phishing-resistant methods, applying sign-in risk policies, blocking legacy authentication and restricting who can register devices. Also review the devices registered to the account, given the registration technique described in the report.

## Conclusion

Device code phishing gets past MFA because the victim really signs in. The most effective defense is to take the flow away from those who do not need it: measure usage, create the policy in report-only mode, keep documented exceptions and turn the block on.
